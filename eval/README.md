# 评测

一个 `eval.py` 回答三个问题：**检索准不准、口径能解释多少、模型有没有说实话。**

```bash
uvicorn app.main:app            # 先起服务，评测打的是真实接口

python eval/eval.py             # 双路评测：/search 测召回 + /query 测拒答
python eval/eval.py --no-query  # 只测检索层，不花 token（改标注后先跑这个）
python eval/eval.py --sweep     # 扫 MIN_SCORE，输出 F1 曲线并给建议值
python eval/eval.py --set-baseline   # 把本轮定为 baseline
python scripts/diff_eval.py     # 之后每次改动只报「哪几个指标动了」
```

产物在 `eval/results/`：`<日期>-<配置指纹>.json`、`latest.json`、`cases.csv`、
`failures.md`、`citation_review.md`。baseline 存在 `eval/baseline.json`。

## 三套口径，一张表

同一批命中，三种算法，**一次采集**（绝不为了三个数字跑三遍——三遍跑出来的排名会不一样，
那样表里的数字没法互相解释）。

| 口径 | 定义 | 回答什么问题 |
| --- | --- | --- |
| 严格 | 只认主承载文档（gold 里没写 `alternate: true` 的锚点） | 「一个答案一个文件」的保守下界 |
| 宽松 | 任一承载文档都算 | 同一句话被两部标准都写了时，不该算检索失败 |
| 端到端 | 检索命中（宽松）且模型确实作答 | 用户问一句，到底多少题真拿到了答案 |

**三个数字必须并列。** 宽松会变好看，所以严格必须在旁边；两者的差额就是「标注口径能解释
多少」，那是分析结论，不是成绩。只报一个，等于用口径偷数字。

## 为什么 gold 允许标多个承载文档

最初的 gold 只许写一个文件，结果 11 道未命中里有几道是「同一句话同时写在两部国标里」——
检索命中了另一部，被记成失败。这不是检索能力问题，是标注口径问题。

所以 `gold` 是列表，一条 gold 可以标 `alternate: true`（同一条规定的另一个合法承载文档）：

```yaml
gold:
  - doc: GB50261-2017_....pdf
    page: 20
    anchor: 压力表量程应为工作压力的2.0倍~2.5倍
  - doc: GB50974-2014_....pdf
    page: 111
    anchor: 压力表量程在没有设计要求时， 应为系统工作压力的2倍～2.5倍
    alternate: true
```

**加这个标记之前必须回库核对原文**，用 `scripts/find_carriers.py` 反查：

```bash
python scripts/find_carriers.py --question n12
python scripts/find_carriers.py --phrase "不应有遮挡物" --yaml
```

要求是「同一条规定」——数值、适用对象、限定条件都要对得上。**同一个主题不算。**
实测过一次打脸：上一轮自认为「5 道跨标准重复」，逐条核对后只有 3 道成立。

- 成立的 3 道：n9（GB50116 6.2.6 与 GB50166 逐字同义）、n12（2 倍～2.5 倍，连「加缓冲装置」
  都一样）、n24（通用规范给原则、专用标准给量化下限，同一要求的两种粒度）
- **不成立的 2 道**：
  - n20 —— 全库只有 GB51251 一处出现那个 10%，GB55036 讲的是余压值 25~50Pa。那是**同章节
    相邻条款的干扰**，标成 alternate 就把「检索选错条款」洗成了「口径问题」。
  - q009 —— 规范侧没有任何一片能单独承载完整逻辑，要 4.8.8 和 4.8.12 两条合起来才等价。
    那是**多跳**，不是口径。

每个 alternate 的题都在 `note` 里写了依据。没有依据的 alternate 一律视为作弊。

## 页码怎么标

`gold.page` 是**切片里的 `page` 字段**，服务端入库时统一成 1 基物理页。除此之外：

- `page_end`：一条长条文跨两页时给区间，`page: 88 / page_end: 89`，落在区间内都算页对得上。
  按条切之后一条条文占几页取决于切片器，不该让标注人去猜。
- 印刷页也认：语料 PDF 的页脚印着原书页码，存在 `page_printed` 里。物理页和印刷页常常差一个
  固定偏移（封面、目录没印页码），标注时照着哪个抄都对得上，不用为了对齐口径重标。

跨标准同义条文（GB50166 6.0.4 ≡ GB51309 7.0.4）入库时会合并成一片，出处记在正本切片的
`also_in` 里。gold 仍按**被并掉的那部标准**标就行——命中正本同样算答对，文字确实在库里，
只是换了件外衣。翻 `eval/results/corpus_audit.md` 能看到完整的 13 组对应关系。

## 第三种失败模式：检索没排到之后

老表里只有「误拒率（阈值口径）」和「幻觉率（无答案题）」，**「检索排到第 7 名、模型看不到、
于是拒答」这类无处安放**。现在单列：

| 指标 | 定义 | 分母 |
| --- | --- | --- |
| `answerable_refused_rate` | 有答案题里模型没给出答案的比例 | 有答案题 |
| `refused_after_miss_rate` | 检索没排进 top-k → 拒答 | 同上 |
| `refused_despite_hit_rate` | 原文就在 top-k 里 → 仍拒答（Prompt / 长上下文问题） | 同上 |
| `answered_after_miss_rate` | 检索没排进 top-k → **照样给答案**（硬答，最危险） | 同上 |

口径要合并两条拒答路径：`abstained`（阈值拦下）**或** 模型自己说「无法回答」。
只看 `abstained` 会得出「0% 拒答」的假象——`MIN_SCORE=0.30` 时阈值路径基本不触发。

`answered_after_miss_rate` 是端到端作答率的反面对照：端到端只看「答没答」，不看「答得对不对」。
检索没排到还硬答的题，在端到端口径里算成功，所以必须单列，否则那个数字会骗人。

四支加起来必须等于 40。对不上就是统计口径写错了，先修代码再解释数字。

**拒答类指标会抖。** 同一套库、同一批题、`temperature=0`，连跑两次的检索指标完全一致
（hit@6 82.5%/87.5%、MRR 0.5887/0.6221，逐题名次也一模一样），但端到端作答率在
**77.5% 与 80.0% 之间跳**，`refused_despite_hit` 从 4 道变 3 道。

原因是模型判「资料够不够」本身就是边界判断，同一道题换个上下文顺序就可能换个结论。
所以：**检索类指标可以当硬数字报，拒答类指标要报区间或跑两次取一致的那部分**，
不要把 2.5 个点的差当成改动生效。

## 指标口径

| 指标 | 定义 | 分母 |
| --- | --- | --- |
| `strict_hit@k` / `loose_hit@k` | 应命中 chunk 出现在前 k 的比例 | 有答案且 gold 解析成功的题 |
| `strict_mrr` / `loose_mrr` | 首个 gold 位次的倒数，未命中记 0 | 同上 |
| `caliber_gap` | 宽松 − 严格 | 同上 |
| `拒答·阈值路径` | 无答案题被 `MIN_SCORE` 拦掉 | 无答案题 |
| `拒答·模型路径` | 阈值没拦、模型自己说「无法回答」 | 无答案题 |
| `真幻觉率` | 两条路都没拦住、模型硬答 | 无答案题 |

`k` 默认 6，**必须等于服务端 `TOP_K`**，否则端到端指标失真（模型看到的是 `TOP_K` 条）。
k=4 时实测有题的正确答案稳定排第 5（n11），直接截断；被截断的题在 `cases.csv` 里归为
「k 截断（排第 N）」。

## 逐题归类：每道题都要能解释

`cases.csv` 每题一行，`category` 列按名次机械判定，可复现：

| 归类 | 含义 | 该怎么办 |
| --- | --- | --- |
| 命中 | 主承载文档进 top-k | — |
| 仅宽松命中 | 只有替代承载文档进 top-k | 口径问题，不是检索问题 |
| 近截断（排第 N） | 排第 k+1～k+3 | 加名额或上 rerank 都能救 |
| 排名靠后（第 N） | 排得更靠后（如第 14） | 加名额是自欺欺人，只能靠 rerank |
| 未进 top20 | 召回就没召回来 | 切片粒度 / 查询改写 / rerank |

`failures.md` 里另有「归因」列是人写的判断，两栏对不上就有一边错。

## 配置指纹

`config_hash` 里含 embedding 模型、chunk 参数、`MIN_SCORE`、`TOP_K`、`k`、`retrieve_k`、
检索模式、BM25/RRF/rerank 参数。

这不是洁癖：**同库同题只换阈值或只换检索模式，指标会整个变一遍**，而这些项不进指纹时
会覆盖同名 json。踩过两次（一次阈值、一次消融模式），都是「数字变了但找不回旧的那份」。

## 失败清单才是资产

`failures.md` 每题给出「归类 / 主承载 / 替代承载 / 实际 top5 / 空的归因栏」。
把归因填完，博客和面试问答的素材就有了：切片切断 / 分词 / 多跳 / 标注错误 / 该扩库。

指标只是门面。

## 引用正确率单独做

`citation_review.md` 抽 20 条，人工判「引用片段是否足以支撑该句结论」，只填三档。
README 里就写「20 条人工抽检，X 完全支持 / Y 部分支持 / Z 不支持」，
**不要换算成百分比**——20 个样本的 95% 置信区间有 ±20 个百分点，撑不住追问。

判定时**必须回库核对被引片段全文**：页面只显示前 200 字，照抄截断内容会误判成不支持。

### 脚本化：`scripts/verify_citations.py`

上面那套人工抽检现在有脚本版：抽答案里每个 `[n]` 所在句的关键数值，回查被引片段里有没有这个数，
出四档结论（支持 / 部分 / 不支持 / 无数值，另有「引用缺失」）。它替代的是「人工挑数值、翻原文、
再记一笔」这三步，**不替代人判断**：

```bash
python scripts/verify_citations.py --base-url http://127.0.0.1:8040
python scripts/verify_citations.py --ids n2 n15 --sample 10 --seed 7
python scripts/verify_citations.py --fail-on-unsupported   # 有「不支持」就退出码 1
```

「不支持」不等于幻觉：换算式、跨片段合并、引用标错都会落进这一档。真正会把报告搞废的是噪声——
第一版把 `GB25201-2010`、`第 1 款`、Markdown 的 `2.`、引用角标 `[3]` 都当成了「关键数值」，
9 条「不支持」里 8 条是这类假阳性，等于报告在报自己。现在这四类都在抽取阶段滤掉了（有单测钉住）。

最新一轮（kb_v2，50 题）：59 条可核对，支持 46 / 部分 13 / 不支持 0。

## 三个会反复踩的环境坑

1. **入库后必须重启服务再评测。** 入库是另起进程写 Chroma，正在跑的服务进程里是旧索引快照。
2. **同一时间只能有一路在跑评测。** 两路并行时会各自写 `latest.json` / `cases.csv` /
   `baseline.json`，还会互相抢 CPU 把延迟打到 700ms 以上。延迟数字只在机器空闲时可信。
3. **rerank 不可用时会静默降级。** 日志只打 WARNING，指标照出——`+rerank` 档位实际等于
   `+RRF` 档位，消融矩阵直接失真。跑消融前必须先确认日志里**没有**「重排不可用」。

## 仓库在 WSL 里、python 在 Windows 上时，另外三个坑

这三个都表现成「卡住或 502」，都不报真实原因，排查一次要花半小时：

1. **`EMBEDDING_MODEL` 写的是 WSL 绝对路径**（`/home/xxx/models/bge-m3`），Windows 侧的 python
   读不到，transformers 于是当成 HF 仓库名去联网下载。跑评测前加 `HF_HUB_OFFLINE=1`，
   并把 `EMBEDDING_MODEL` 覆盖成 `models/bge-m3`（`_resolve_source` 现在会直接抛错）。
2. **`chroma_db/` 落在 `\\wsl$` 这种 UNC 路径上**，`chromadb.PersistentClient` 初始化会卡住。
   把 `CHROMA_DIR` 指到本地盘（`D:/.../chroma_kb2`）即可，WSL 侧照样能通过 `/mnt/d/...` 读。
3. **`http_proxy` 劫持本机请求。** 环境里 proxy 指向某个本地端口时，`urllib` 连 `127.0.0.1`
   也走代理，报出来是 502。`eval.py` 与 `verify_citations.py` 里已固定用不代理的 opener，
   命令行手测时仍需 `NO_PROXY=127.0.0.1`。
